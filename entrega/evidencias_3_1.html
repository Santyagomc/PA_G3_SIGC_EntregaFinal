1. Arquitectura en ejecución

La solución completa se levanta con docker compose up --build -d desde la raíz del proyecto. Servicios: MariaDB (db), Apache Kafka en modo KRaft (kafka), creación de tópicos (kafka-init), Kafka UI (kafka-ui), Redis (redis), API REST Spring Boot (api), gateway GraphQL (gateway) y frontend Angular servido por nginx (frontend).

Frontend Angular (:4300) ──REST──► API Spring Boot (:8080) ──► MariaDB (:3307) │ ▲ └─ outbox ─► Kafka audit-events ─► sigc-audit / sigc-notifications └──GraphQL──► Gateway (:8081) ──┘ └─ errores ─► audit-events.DLT ─► sigc-dlt JWT+roles · CORS · timeout/retry/circuit breaker · caché Redis (:6379) Kafka UI (:8090) para inspeccionar tópicos, mensajes y grupos de consumidores

2. Flujo de uso principal

  1. Login (mutation login en el gateway o POST /auth/login): se obtiene un JWT con el documento y el rol del usuario.
  2. Radicar PQR (radicarSolicitud / POST /requests/save): la API valida, aplica el motor de reglas legales, guarda la PQR y registra el evento REQUEST_CREATED en el outbox en la misma transacción.
  3. Cambiar estado (cambiarEstadoSolicitud, solo ADMIN): se registra REQUEST_STATUS_CHANGED.
  4. Kafka: el relay publica en audit-events; sigc-audit escribe el historial y sigc-notifications registra la notificación al ciudadano (correo simulado).
  5. Consulta por GraphQL: solicitud(id){ ... historial{...} } compone la PQR y su historial desde dos endpoints REST, devolviendo solo los campos pedidos.
  6. Indicadores del tablero: resumenIndicadores (en caché Redis) alimenta las tarjetas del dashboard del frontend.
  7. Seguridad y resiliencia: se prueba acceso permitido y denegado, y la respuesta del gateway cuando la API no está disponible (circuit breaker).
